  Orbit lines with approach-driven opacity — design

  New module spacesim/orbit_lines.py (pure numpy, no GL — same split as
  body_style.py). rendering.py is already 4121 lines; the maths does not belong
  in it. The module owns three things:

  1. ellipse_points(body, segments) — the faint full orbit. r = a(1−e²)/(1+e·cos
  φ) over a vectorised φ grid, rotated by arg_periapsis — the dead _draw_orbit
  at rendering.py:2516 omits that rotation, so its ellipse is wrong for any body
  with a non-zero periapsis argument (all zero in solar_system.json today, but
  world.py:690 sets it in epicycle mode). The parent-relative offsets depend
  only on (a, e, arg_periapsis, segments), so they're cached per body and the
  per-frame work is one array add plus the projection. That dead method gets
  deleted rather than left as a second, wrong copy.

  2. future_track(body, times) — the bright in-horizon arc. A batched,
  operation-for-operation transcription of body.position_at_time, including the
  parent chain (memoised per body, so Saturn is solved once for six moons).
  Using the same constant-angular-rate model the predictor's gravity uses is the
  point: the arc agrees with where the drawn line actually goes. times is
  linspace over the prediction's own time window [points[0,2], points[-1,2]], so
  +/− on the horizon lengthens the arc for free.

  3. approach_alpha(...) — the fade. Predictor line resampled at those same
  times via np.searchsorted on the t column, distance to the track per sample,
  argmin, then a quadratic refine through the three samples around the minimum
  (5 lines, removes most of the sampling error — at 192 samples the raw argmin
  can be off by ~½ sample step ≈ 0.25 SOI, which is 13 % of the ramp). Then

  soi   = a · (m / m_parent)^0.4
  u     = (miss/soi − soi_fade) / (soi_full − soi_fade)      # 3→0, 1→1
  alpha = max(floor, alpha_max · smoothstep(clamp(u)))

  floor = 0.10, or 0.35 for the reference body and the selected body. The same
  alpha scales both the ellipse and the arc (arc × a brightness multiplier), so
  they fade as one object.

  Sanity check on the shipped numbers, LEO → Mond (SOI 66 170 km): dark below
  apoapsis ≈ 186 000 km, half-lit at ≈ 250 000, essentially full at ≈ 318 000.
  The arc only reaches as far as your prediction horizon does, so a short
  horizon legitimately shows nothing — that's the intended semantics, not a bug.

  Recompute cadence. The metric is keyed on predictor._points_generation plus
  "sim time has moved more than one track sample step" — which self-scales with
  the horizon and covers the warp hold, where the generation doesn't bump.
  Between recomputes the drawn alpha eases toward the target with the project's
  1 − exp(−rate·dt) off real_dt, so a coarse update rate is invisible.

  Drawing — Renderer._draw_orbit_lines(bodies, camera, predictor), called in
  render() right after _draw_reference_trajectories, inside the FXAA target,
  before the bodies (so bodies occlude their own orbit line). Projection goes
  through frame.to_this_frame_xy_arrays(times, xs, ys) — the documented batch
  path, same as _project_prediction_batch — with the scalar _frame_transform_xy
  loop as fallback when it returns None. The ellipse passes a constant
  _frame_time_s; the arc passes each sample's own time. Culling copies
  _draw_reference_trajectories: vectorised bbox reject, plus a min_screen_px
  collapse test, plus adaptive segments from screen circumference clamped to
  [64, 512]. Bodies with no is_moon_of (Sonne) and ships are skipped — no
  parent, no orbit.

  One deliberate visual property to flag: in a rotating body-direction frame the
  faint ellipse is the instantaneous locus at the current frame time, while the
  bright arc is time-correct per sample. They will visibly disagree there. That
  disagreement is the truth — an ellipse has no single time — and it's the same
  convention the reference trails already use.

  What I found along the way

  Three inconsistent body-motion models exist in this codebase, and they matter
  here. bodies.position_at_time freezes the angular rate at the epoch (what the
  predictor uses), reference_frames solves Kepler properly (the frame origin),
  world.update_planets integrates dθ/dt = v/r. They agree exactly at t=now and
  then diverge:

  ┌──────┬────────┬────────┐
  │      │ 3.8 d  │  30 d  │
  ├──────┼────────┼────────┤
  │ Erde │ 0.5 px │ 241 px │
  ├──────┼────────┼────────┤
  │ Mond │ 11 px  │ 768 px │
  └──────┴────────┴────────┘

  I use the predictor's model, because then both lines take the same transform
  and the difference is common-mode — it cancels in the cap comparison. But it
  means the prediction itself is unreliable much past a week, which caps how far
  the readout can be trusted. That's pre-existing, not introduced here, and
  it's now documented with the numbers.

  frame.set_origin_interp_window() would have made the projection nearly free,

  non-rotating frame has zero rotation and a curved origin; measuring only the
